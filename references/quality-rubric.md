# Quality Rubric — Non-Negotiable Rules

Every bank generated by `code-study-quiz` must comply. These rules were
distilled from the MCB pilot (150 questions across 4 files), where each rule
corresponds to a real failure mode observed during reviews.

## 1. Format

- **MCQ only.** Exactly 4 options labelled A–D. Never V/F, never matching,
  never fill-in-the-blank.
- **One unambiguously correct answer.** No "most correct" debates; no
  multiple-correct; no "todas las anteriores", "ninguna de las anteriores",
  "A y B".
- **No double negatives** in the stem. No tricky "NO/NOT" framings.
- **No absolutes** ("siempre", "nunca") unless factually grounded in the
  source.

## 2. Pre-lectura — autocontenida

The student must be able to answer reading **only** the pre-lectura. The
optional `archivo:línea` (Técnica) or Confluence link (Funcional/Mixta) is
support, not a requirement.

If a pre-lectura forces the reader to open the code or the document, it is
not autocontained — rewrite it.

## 3. Snippet fidelity (Técnica/Mixta)

- The code shown is **real code**, copied (not paraphrased) from the source
  file.
- The `archivo:línea` ref points to the actual location (line numbers may be
  ±2 due to formatter drift; symbols and content must match).
- **Non-contiguous lines are never presented as contiguous.** Insert a `// …`
  line wherever intervening lines are omitted. Example:

  ```ts
  entity CostCenterBudgets : cuid, managed {
    // … (campos no relevantes para la pregunta)
    costCenter : Association to CostCenters not null @mandatory;
    // …
    assets : Composition of many BudgetAssets on assets.budget = $self;
  }
  ```

## 4. Distractors

- All 4 options plausible to someone who skimmed the pre-lectura. No throwaway
  absurd options.
- Similar **length, grammar, register** to the correct option. The correct
  answer must not stand out by being notably longer, shorter, more technical,
  or grammatically tighter.
- The explanation in `<details>` must touch **each** distractor and explain
  why it fails — not just praise the correct one.

## 5. Correct-letter balance

For files of N≥40 questions, target roughly 25 % per letter; **never let any
letter be 0**.

| N    | Min per letter         |
| ---- | ---------------------- |
| 40   | ≥ 8 (so ≥8 D and ≥8 A) |
| 30   | ≥ 6                    |
| ≤ 20 | ≥ 3                    |

A skewed distribution (e.g. 0 D, 14 B in 30 questions) is a **psychometric
defect**: test-savvy readers exploit the pattern. The fix is to **reorder the
4 options within questions and update the bold letter in `<details>`** — never
change the actual content.

## 6. No duplicated facts

Two questions must not test the same atomic claim, even phrased oppositely
(e.g. "in which state can X be deleted?" vs "which states block deletion of
X?" — same fact). If detected during review, replace one with a different
documented fact.

## 7. Ordering and IDs

- Questions appear in strict **Bloom order**: all [Básico] first, then all
  [Intermedio], then all [Avanzado].
- IDs `P-{f}.{n}` are **sequential within each file**, starting at 1, no gaps,
  no duplicates.

## 8. Sources and links

- Functional pre-lecturas link to the source doc when applicable. The URL
  scheme is provided by the user during BUILD (e.g.
  `https://syntax.atlassian.net/wiki/spaces/IOT/pages/{PAGE_ID}/`). The skill
  does not assume a specific scheme.
- `IOT` (or whatever space the user supplies) is **literal**. Reviewer
  subagents must not "correct" it to a numeric space ID without the user's
  confirmation.

## 9. CAP / framework-critical lens

When the codebase uses a framework with non-obvious mechanics (CAP drafts,
composition SAVE handlers, projections-with-filter, `@flow.status`,
authorization annotations, etc.), the generator subagent must actively
identify those points and produce at least a handful of questions on them —
they are where readers most need help.

## 10. Process discipline (controller)

- Implementer subagents **write files but do not commit**. Reason: sandbox
  blocks `.git/.../index.lock` and nested sub-repos compound the issue.
- The controller commits with `dangerouslyDisableSandbox: true` applied
  **only** to the `git commit` call.
- Spec compliance and code/question quality are reviewed in a **single
  combined pass** (saves a full review cycle without losing rigour — the
  separate-stage workflow added cost without proportional gain in MCB).

## Red flags during review — STOP and fix

- Snippet shows code that doesn't exist in the file.
- Two adjacent question IDs test the same fact.
- All correct letters in a file are B/C (D = 0).
- An option is much shorter/longer than its siblings.
- The explanation in `<details>` mentions only the correct option.
- Pre-lectura ends with "…see the doc for details" — not autocontained.
